# Research: 운영 이미지 Storage 활성화

## 비공개 버킷과 RLS

**Decision**: 사례 원본, 사례 검토본, 랜딩 대표 이미지 모두 비공개 버킷으로 유지하고 작업별 RLS 정책을 적용한다.

**Rationale**: 비공개 버킷은 다운로드에도 RLS가 적용되며, 제한 시간 서명 URL로만 방문자에게 파일을 제공할 수 있다. 업로드는 `INSERT`, 결과 반환과 관리자 미리보기는 `SELECT`, 교체는 `UPDATE`, 삭제는 `DELETE` 정책이 필요하다.

**Alternatives considered**: 공개 버킷은 CDN 효율은 높지만 URL을 아는 사람이 초안이나 폐기 전 이미지를 계속 조회할 수 있어 게시 상태 연동 요구에 맞지 않는다.

## 공개 읽기

**Decision**: 사례 검토본은 기존 사진 행의 공개·준비 상태와 사례 게시 상태를 확인하고, 랜딩 대표 이미지는 현재 게시 콘텐츠의 저장 경로와 일치할 때만 서명 URL 발급을 허용한다.

**Rationale**: 데이터 공개 상태를 Storage 정책의 기준으로 삼으면 UI 숨김에 의존하지 않고 비공개 객체 접근을 차단할 수 있다.

**Alternatives considered**: 공개 URL 저장은 단순하지만 게시 취소 후에도 URL을 통한 접근을 즉시 막을 수 없다.

## 객체 삭제와 보상

**Decision**: Storage 객체 삭제는 Storage API로 수행한다. 업로드 후 메타데이터 저장이 실패하면 해당 요청에서 생성한 객체를 제거하며, 개별 사진 삭제는 객체 삭제 성공 후 사진 행을 갱신한다.

**Rationale**: Storage 메타데이터 테이블을 직접 삭제하면 실제 객체가 남아 비용과 고아 데이터가 발생할 수 있다. 순차 보상은 브라우저 기반 작업의 부분 실패를 명시적으로 복구한다.

**Alternatives considered**: DB 트리거에서 Storage 객체를 삭제하는 방식은 Storage API를 우회하므로 사용하지 않는다. 장기 보존 큐는 현재 규모에 과도하다.

## 랜딩 이미지 수명주기

**Decision**: 새 이미지를 먼저 업로드하고 경로를 초안에 저장한다. 게시본·초안·버전 기록에서 참조되는 객체는 유지하며, 안전한 정리 후보만 별도 삭제한다.

**Rationale**: 사이트 콘텐츠 버전 복원을 지원하므로 단순 교체 즉시 삭제는 이전 버전을 깨뜨린다.

**Alternatives considered**: 영구 보존은 안전하지만 고아 파일이 누적된다. 즉시 삭제는 버전 복구 요구와 충돌한다.
