# 연결된 Supabase 운영 DB 감사 · 2026-10-23

검증 시각: 2026-10-23 22:25 KST. `specs/010-admin-figma-refresh/tasks.md` T007과 기존 `009-admin-operations` 계약을 기준으로 연결된 운영 프로젝트를 확인했다. 기존 연결 자격증명을 사용했으며 비밀값·계정 식별자·문의 본문은 기록하지 않았다.

## 결과

`20261023000100_operations_privileges.sql`을 적용해 운영 객체 7개의 불필요한 API 역할 권한과 감사 시퀀스 접근 권한을 제거했다. 적용 후 로컬·원격 마이그레이션 **17개가 일치**하며 최종 `db push --linked --dry-run` 결과는 `upToDate=true`, migrations/seeds/roles 모두 빈 배열이다.

적용 전후 **앱 테이블 34개의 모든 행**을 DB 내부에서 계산한 비교값으로 대조해 동일함을 확인했다. Storage 버킷 5개의 공개 여부·용량 제한·MIME 설정도 동일하며 모두 private다. 데이터 재설정·시드·운영 정책 게시·사례 상태 변경·파일 삭제는 수행하지 않았다.

## 발견한 원인과 수정

Supabase의 `public` 스키마 기본 권한은 새 테이블·뷰·시퀀스·함수에 `anon`, `authenticated`, `service_role` 권한을 부여한다. 기존 격리 PGlite 검증은 이 기본 권한을 재현하지 않아, 명시적인 REVOKE가 없는 다음 객체의 과도한 권한을 놓쳤다.

| 대상 | 수정 전 | 수정 후 |
|---|---|---|
| `content_documents`, `content_document_versions` | anon 전체 권한, authenticated 쓰기·TRUNCATE 포함 | anon 권한 없음, authenticated SELECT만 |
| `case_revision_drafts`, `case_revision_history` | 동일 | 동일 |
| `media_assets`, `media_cleanup_jobs` | 동일 | 동일 |
| `admin_activity_feed` 뷰 | 동일 | 동일 |
| `admin_activity_logs_id_seq` | anon/authenticated USAGE·SELECT·UPDATE | 두 역할의 권한 없음 |

기존 RLS는 행 접근을 제한하고 있었으므로 이를 데이터 유출의 증거로 해석하지 않는다. 다만 TRUNCATE는 RLS 적용 대상이 아니며 불필요한 직접 쓰기 권한 자체를 제거해야 한다. 수정은 PUBLIC/anon/authenticated의 해당 객체 권한을 회수한 뒤 authenticated SELECT를 명시적으로 다시 부여한다. 서비스 역할 권한, RLS 정책, RPC 정의, 데이터 구조는 유지한다.

격리 검증은 실제 PostgreSQL 엔진에서 동작하지만 Auth/Storage 객체는 fixture다. 원격 역할 검사는 읽기 전용 SQL 역할 전환이며 브라우저 로그인 E2E와 구분한다. 운영 접근 검사는 읽기 전용 트랜잭션으로 제한했고 TRUNCATE는 원격에서 시도하지 않았다. 감사 중 cleanup 후보 RPC가 내부 DELETE를 수행하는 것이 읽기 전용 트랜잭션에서 차단되어, 최종 검사는 해당 RPC의 실행 권한 조회로 교체했다. 그 시도에서 운영 변경은 발생하지 않았다.

동시에 진행 중인 UI 변경에 대해 22:25:29에 실행한 전체 `pnpm test`는 64개 파일 중 63개 통과, 258개 테스트 중 257개 통과였다. 실패 1개는 `tests/component/inquiry-list-layout.test.tsx`의 `내 담당` 링크 기대이며 당시 문의 UI 구현이 진행 중이었다. 이 기록은 DB 검증 통과와 별개이며, 전체 UI 완료 판정은 후속 전체 검증 기록을 따른다.

## 실제 스키마 대조

로컬 migration을 적용한 격리 DB와 원격 카탈로그를 대조했다. PostgreSQL 버전에 따라 NOT NULL이 `pg_constraint`에 별도 표시되는 차이는 제외하고 열 nullable 속성으로 비교했다.

| 객체 | 수 | 결과 |
|---|---:|---|
| public/private 테이블·뷰 | 35 | 일치, RLS 활성 여부 포함 |
| 열 | 275 | 기존 서비스 slug 기본값 1건만 차이 |
| 제약조건 | 161 | 일치 |
| 인덱스 | 59 | 일치, invalid/not-ready 인덱스 없음 |
| public/private/storage RLS 정책 | 51 | 일치 |
| 앱 함수 | 90 | 본문 해시·시그니처·security definer·search_path·역할별 실행 권한 일치 |
| 앱 트리거 | 19 | 일치 |
| API 역할 테이블 권한 항목 | 247 | 일치 |

기존 차이: 로컬 최초 migration에는 `services.slug`의 `case-<UUID>` 기본값이 있으나 원격에는 기본값이 없다. 현재 정해진 서비스 4개의 slug와 운영 편집은 그대로 유지되며 이번 권한 보정에는 이 차이를 섞지 않았다. 이미 적용한 과거 migration을 다시 실행하거나 수정하지 않았다.

외래키 선두 인덱스가 없는 제약 30개도 확인했다. 감사/작성자 참조와 문의 하위 테이블 등이 포함되며, 실제 부하·지연 문제를 증명하는 근거 없이 일괄 인덱스를 추가하지 않았다. 현재 정의된 59개 인덱스는 모두 유효하다.
